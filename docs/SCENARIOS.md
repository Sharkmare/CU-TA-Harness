# Scenarios that need two games

A scenario drives a host game and a client game through the link, does one thing on the client and reads the authoritative state on both. This document describes the engine and the building blocks. The scenarios themselves are yours to add; `docs/ARCHITECTURE.md` says where they go (`client/scenarios/`, or `local/scenarios/` for work that is specific to you).

## The scenario engine

The engine is `casualtieslink/scenarioengine/desync.py`. A `Scenario` has a name, a `prepare(host, client)` that picks a target and returns a context, an `act(client, context)`, a `read(game, context)` that returns the state to compare, a `changed(value, baseline)` and sample offsets in seconds. A `SeriesScenario` samples continuously while the client acts (held clicks, repeated swings) and runs once per network profile. Each scenario ends in one verdict: `persisted` (both agree and the change is there from 0 s), `reverted-by-host` (the client had the change and it was overwritten with the old value), `diverged` (the games disagree), `not-there-from-the-start` or `never-changed`. The test passes only on `persisted`. The report prints the baseline and the host and client value at each time, marks rows where the games disagree, names the build and the SHA-256 of its plugin DLL, and is saved as JSON under `.state/desync_reports/`. A scenario can define its own `check(context)` that returns issues; an issue starting with `INVALID` or `NOT COUNTED` means the run does not count.

Scenarios that share a build and startup flags run inside one launch of the host and the client, one after another (`scenarioengine/launchplan.py` groups them). Each scenario picks its own target again and starts by emptying the client's hand and releasing input, so the verdicts are independent. A scenario that fails in its setup fails alone; the launch goes on. A scenario module registers its scenarios by extending `scenarios.desync_scenarios.SCENARIOS` or `SERIES_SCENARIOS`; `scenarios/desync_scenarios.py` also holds the helpers most scenarios need (positions and distances, spawning and finding objects, held-click mining, aim patterns, fresh block placement, `ready_up`) and the preflight registry (`PREFLIGHTS`): before any game starts, the runner asks every registered preflight to check its planned counts against `--repeat`; a contradiction prints `PREFLIGHT:` lines and exits 2 without launching.

## Builds

A build is what is installed into a game copy before a launch. The registry is `local/builds.json`, documented in `casualtieslink/games/buildregistry.py`: flavour builds (the flavour package zip named by `CU_FLAVOUR_ZIP`, started with `--mp-flavour`), stage builds (a folder with `plugins/Together` and optional library plugin folders, located by an environment variable or a path under the mods root) and python builds (a function that installs the copy). The same file lists the plugin sets a scenario can ask for (`dll`, `directory`, `release-zip`). Without it only `stock` (the folder in `CU_STOCK_TOGETHER_DIR`) and `keep` exist. Builds are chosen with `--together` or listed with `--builds`; the test class name carries the build and the first eight hex digits of its DLL hash, and a test checks that both games run the DLL with that hash. Every report names its launch, repetition, game version, network profile and proxy seed.

`games/instances.py` makes the two copies (`%TEMP%\CU-scenario-host` and `%TEMP%\CU-scenario-client`) once and, before every scenario, rebuilds each copy's plugin set: it removes the plugin folders the registry manages, installs the chosen build, copies the freshly built link plugin (`dotnet build plugin -c Release`, or `CU_LINK_DLL`) and installs the plugin sets the scenario names. The operator's game folder is only read. The profile folder and PlayerPrefs are saved and restored around the whole run, and a persisted "Together disabled" preference is set back to enabled for the run.

## The network proxy

The client connects to the host through a UDP proxy (`casualtieslink/games/udpproxy.py`, client port 7791, host 7790). Its network profile changes while the games run, without dropping the connection: `delay_ms`, `jitter_ms`, `loss` and `reorder` (the share of packets that get 30 ms extra, so they can arrive late). Jitter, loss and reorder draw from a generator seeded per launch, and the seed is in the report. Packets keep their order in each direction while jitter and reorder are 0 and the delay does not change; jitter, reorder and lowering the delay mid stream can let a later packet overtake an earlier one. `proxy.set(delay_ms=100, jitter_ms=60)` is the Python interface. A loopback only HTTP control (`GET /get`, `POST /set` with a JSON object) is off unless the launcher starts it with `proxy.start_control(port)`; it refuses any peer that is not loopback and any other `Host` header.

Stall and flush approximates a link that goes quiet and then delivers everything at once (the way a relayed connection behaves). For the client to host direction (and the host to client direction when `stall_to_client` is 1) the proxy holds every packet for a random stretch and then releases all held packets back to back, in arrival order, `stall_gap_ms` apart (default 0); after that the normal delay and jitter resume. A stall starts a random time after the previous one ended, uniform in `stall_interval_ms` +- `stall_interval_spread_ms`, and lasts uniform in `stall_duration_ms` +- `stall_duration_spread_ms` (each spread at most its mean; a mean of 0 for the interval or the duration switches stalls off). The stall draws use their own generator seeded from the proxy seed, so switching a stall on does not change the jitter sequence, and the stall never drops or reorders a packet: held packets leave in arrival order, a flush waits for any earlier packet still in flight, and a later packet is never due before the last flushed one. Every finished stall is in `proxy.stall_trace` (direction, start, end, packets held, first and last release time, gap) and in the report as `stallTrace`; `proxy.trace_since(mark)` lists every packet as (received at, direction, size, delay ms, due at), with the due time of a held packet being its release. Profiles carry the stall after the four network values: `--net DELAY:JITTER:LOSS:REORDER:STALL_INTERVAL:INTERVAL_SPREAD:STALL_DURATION:DURATION_SPREAD:GAP:TO_CLIENT`, for example `--net 100:75:0:0:800:300:400:100` is 100 ms delay, up to 75 ms jitter and a stall every 0.5 to 1.1 s that holds packets for 0.3 to 0.5 s. `tools/proxy_mutation_check.py` proves the stall tests fail when the mode is broken.

A scenario that depends on the network (the series scenarios) runs once per profile of `--net DELAY:JITTER[:LOSS[:REORDER]]`; the other scenarios run once. The runner applies the profile before each scenario and restores a direct link after it. `--repeat N` runs every scenario N times inside the same launch. A profile can carry its own repetition count, `DELAY:JITTER@COUNT`.

```bash
python client/run_tests.py --pair --only <group> --builds build-a build-b --net 100:0 100:60 250:100 --repeat 3 --match <name fragment>
python client/run_tests.py --only <group> --builds build-a --net 100:0 --list
python client/run_tests.py --pair --only <group> --together build-a --budget-seconds 600
python client/run_tests.py --pair --only <group> --together build-a --mutate skip-client-action
```

`--builds` plans one launch per build and startup group and prints the launches, their scenario runs and how many launches one launch per run would have needed; with `--pair` it runs them, each launch as its own process with a time budget of 60 s per scenario run plus the startup. `--list` stops after the plan. `--together` runs a single launch. A series scenario also has its own budget of 120 s per run. `tools/desync_summary.py` sums the reports of one launch per network profile: blocks mined, blocks that reappeared, swings sent, received and accepted, losses by reason, and the delay the proxy planned. `tools/mining_summary.py` does the same per run for held-click mining reports (the report file pattern is `CU_MINING_REPORT_PATTERN`).

## Position control

A scenario that swings holds the bodies instead of letting them stand free. `casualtieslink/scenarioengine/positioncontrol.py` wraps the `hold_body` link commands: `place_and_hold` seats a body and proves it stays within the tolerance over several polls, `seat_pair` holds the attacking client at its seat and parks the other player 12 units away, `preflight_pair` checks both bodies are at their targets within the tolerance and at least 2.0 apart, and `start_positions` records both bodies at the start of a run. A seat that fails its verification is released and tried again, up to 3 attempts; `seatAttempts` and `earlierAttemptIssues` are in the report.

Bodies have roles. A body that takes part in the swing (the attacking client, and the victim of a punch) is held to 0.05 and its seat is accepted only when the holder's own view (`hold_status`) and `rb.position` both sit within 0.05 of the target and of each other (`judge_seat`, `verify_swinging_body`, `preflight_views`); the link position read is recorded next to them and a disagreement is reported as `linkReadDisagrees`, it does not fail the seat. A body that is only parked is held at `PARKED_TOLERANCE` (0.5, a recorded number, not an abort) and judged by distance only: at least 6 units from the client and the target by the nearest of its readable position reads (`parked_distance_problems`), at the preflight and at every swing; a closer reading marks the run confounded, drift is recorded, never a failure. A run that fails its preflight is marked `INVALID`: a setup failure, never a valid run or a missed swing. `tools/recover_after_abort.py` stops stray games, restores the profile and deletes the scenario copies and a stale lock after an aborted run.

## All or nothing swings

A swing scenario run is all or nothing. A missed swing fully invalidates a test, so setup must make a setup-caused miss impossible (`casualtieslink/scenarioengine/swinggate.py`). Every swing is gated immediately before it fires, from fresh reads: the body within 0.05 of its seat by the holder's view and `rb.position`; limb 1 within 0.5 of its rest pose relative to the body (limb 0 is recorded, not gated: it is not the swing origin and it moves with the swing animation) and limb 1 within 4.5 of the target (the game's attack distance); `isRight` matching the side of the target; the attack cooldown ready; the target present with health, its copy state (bodyType, physicsActive) recorded on both machines; the distance inside the band; and no other body within 6 units of the body or the target. The gate is read until it passes (`wait_ready`, 0.1 s polls, 3 s timeout) because the limb and the body are in recoil for a moment after a swing; the passing read is fresh and the swing is fired at once. A swing whose gate has not passed within the timeout is not fired and the run is INVALID, with the gate named. After any move or teleport the swings wait until both limbs keep the same place relative to the body on two consecutive reads and limb 1 is within reach of the target (`settle_limbs`, 6 s timeout, then INVALID); that read is the rest pose. A swing fired with every gate passed that still did not land makes the run a FAIL, a finding about the product, reported apart from INVALID; the gate values at fire time stay in every swing record (`gate`). A run is valid only when every swing landed, so reports show runs (valid n of m) and the invalid and fail lists, never partial swing counts. `python tools/gate_mutation_check.py` mutates each gate and the verdict and fails when a mutation is not caught by `unit/test_swinggate.py`.

`scenarios/swing_driver.py` fires one swing (the attack call that raises the cooldown, counting the ignored attempts) and `scenarios/band.py` re-seats the client until it stands inside a distance band of a target; both are the blocks the swing scenarios are built from.
